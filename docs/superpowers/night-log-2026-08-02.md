### Iteration 1 — `perf/optimize-fs-walker-17365163716527261640` → DROP

Commit `570a230` "⚡ Optimize file system traversal using os.scandir", 1 file,
+60/-15 in `arcade_scanner/scanner/file_system.py`.

**Cherry-pick onto the work branch conflicts** (`UU file_system.py`, aborted
cleanly). The branch was written against a much older `file_system.py`; `dev`
has since rewritten `_walker_worker` substantially.

**Applying it would regress three things that landed on dev afterwards:**

1. *Queue protocol.* The branch does `queue.put_nowait(entry.path)` — a bare
   string. `scanner/manager.py:249` unpacks `async for file_path, dir_changed in
   fs_scanner.scan_directories(...)`. Bare paths raise `ValueError` on the first
   file: the scanner would be dead on arrival.
2. *Backpressure.* Dev deliberately uses a bounded `Queue(maxsize=500)` with a
   blocking `run_coroutine_threadsafe(queue.put(...)).result()` — the comment
   calls it "natural backpressure". The branch's `call_soon_threadsafe(
   queue.put_nowait, ...)` is non-blocking and would raise `QueueFull` past 500
   queued paths, exactly the memory-explosion case the bound exists to prevent.
3. *Incremental scan.* Dev skips directories whose `mtime` predates
   `_last_scan_time` and reports `⚡ Skipped N unchanged directories`. The
   branch has no notion of this and would rescan everything every time.

**And the payoff does not justify re-implementing the idea on top of dev.**
Benchmarked both traversal strategies with identical filter semantics on a
synthetic tree (300 dirs, 12 000 files, 2 exclusions, warm cache, median of 7):

```
os.walk    median  21.0 ms   best  20.4 ms   2630 hits
os.scandir median  19.0 ms   best  18.9 ms   2630 hits
→ scandir +9.7% faster; identical result sets
```

Real but irrelevant: ~2 ms saved per 12 000 files. A scan's cost is dominated by
one `ffprobe` subprocess per *new* file (tens to hundreds of ms each), and the
incremental-scan skip that dev already has is the far larger lever. Optimizing
the walker trades a guaranteed regression for noise-level gains.

**Proposed for the morning:** delete `origin/perf/optimize-fs-walker-17365163716527261640`
(the loop does not delete branches itself). Benchmark script kept at
`docs/superpowers/bench/bench_walker.py` so the measurement is reproducible.

### Iteration 2 — `perf-duplicate-detector-bktree` → DROP the branch, but it found a real bug

**⚠️ Read this section first in the morning — it contains the night's most
important finding, and it is not about the branch.**

#### The branch itself: superseded

Commit `202bf8d` adds a BK-tree to replace an O(n²) all-pairs loop in
`_find_image_duplicates_by_hash`. That loop no longer exists — `dev` has since
replaced it with exact-hash bucketing plus a prefix-bucket near-miss pass. The
branch's tip commit is "Stop work on obsolete PR". Nothing to merge.

#### But the thing that replaced it is broken

The prefix-bucket pass grouped hashes by their first 4 hex chars and only
compared *within* a bucket, justified by this comment:

> images with different prefixes have hash distance > 16 bits, so can't match at
> threshold ≤ 5

That reasoning is wrong. A 4-char prefix bucket holds hashes whose leading 16
bits are *identical*. Two hashes differing by a single bit inside those leading
16 bits land in different buckets and are never compared — despite a Hamming
distance of 1, far below the threshold of 5.

Confirmed by a characterization test before touching anything: two hashes one
bit apart in the *last* bit are grouped, the same two one bit apart in the
*first* bit are not. Same distance, opposite outcome.

Measured against brute force as ground truth (5000 hashes, threshold 5):

```
      n      brute     prefix     banded    prefix recall  banded recall
    500      95.9ms       0.1ms       2.4ms            43.6%         100.0%
   2000    1566.6ms       0.6ms      18.3ms            40.2%         100.0%
   5000    9871.6ms       1.7ms      85.2ms            43.8%         100.0%
```

**The shipped duplicate finder was missing roughly 56% of near-duplicate image
pairs.** Exact duplicates were always found (that is a separate O(n) pass) — the
loss is confined to near-misses, i.e. re-encodes, resizes, and re-saves, which
is precisely what perceptual hashing exists to catch.

#### The fix

Replaced prefix bucketing with a banded index (`_BandedHashIndex`): each hash is
split into `threshold + 1` bands and indexed per band. A pair within the
threshold differs in at most `threshold` bits, which can touch at most
`threshold` bands, so at least one band survives intact — a lookup across a
hash's own bands returns every true match. Pigeonhole principle; no false
negatives by construction, and verified empirically against brute force.

The BK-tree from the branch was also implemented and measured first. It is
exact but slow — 5202ms at n=5000, only 2× faster than brute force, because at
threshold 5 the pruning window is wide relative to how random 64-bit hashes
distribute. Banding is ~60× faster than the BK-tree at the same recall, so the
branch's data structure was discarded in favour of it.

Distance comparison switched from `imagehash.ImageHash.__sub__` to integer
popcount: identical results, 637ms → 43ms over 780 758 candidate checks, since
the operator routes through numpy. Guarded with a `bin(x).count("1")` fallback
because `pyproject.toml` declares `requires-python = ">=3.8"` while `int.bit_count`
needs 3.10. (Note the inconsistency: README says "Python 3.10+".)

Cost of correctness: that phase goes from 1.7ms to 85ms at n=5000. Worth it.

**Tests:** `tests/test_duplicate_detector.py`, 7 tests — the head/tail asymmetry
pair, exact matches, distant hashes, `threshold=0`, vanished files, and a
randomized test comparing against brute force. Verified they fail against the
old implementation (2 failed) and pass against the new (7 passed); the
randomized one independently caught a dropped pair.

**Proposed for the morning:** delete
`origin/perf-duplicate-detector-bktree-8262525754746318244` — its idea is now
implemented better, in `dev`'s lineage rather than against a two-refactors-old base.

### Iteration 3 — `fix-json-store-concurrency` → DROP, but it pointed at a live bug

**⚠️ This iteration found a production race in the encoding queue. Read it.**

#### The branch: nothing left to merge

Two commits. `d2bca17` adds `import threading`, a `self._lock`, and five `with
self._lock:` blocks to `JSONStore`. `944b389` — "Abandon PR due to merge
conflicts" — **takes them all back out**. The net diff against the merge base is
whitespace only: five trailing-space removals in a file nothing imports.

`json_store.py` is confirmed dead. A repo-wide search for `json_store` /
`JSONStore` (py, js, json, md, sh, toml) finds only: the module defining itself,
two docstring references in `sqlite_store.py` ("Drop-in replacement for
JSONStore"), a historical note in `dev-docs/performance-roadmap.md`, and the
stale claim in CLAUDE.md that it is "the legacy format migrated at startup".

#### The concern behind it, checked against the store that actually runs

The branch worried about unsynchronised access to the store. `SQLiteStore` does
hold a `_write_lock` and does use `check_same_thread=False` — but the lock
covered only the media-table writes (`upsert`, `bulk_upsert`, `remove`,
`delete_all_photos`). **Every `encoding_queue` method ran unlocked**, including
`get_next_pending`, whose docstring reads "Atomically claim the oldest pending
job".

It was not atomic. It ran a SELECT and then a separate UPDATE — on a connection
opened with `isolation_level=None`, i.e. autocommit, so the two statements are
independent transactions with nothing held between them. The UPDATE did carry
the right compare-and-swap guard (`WHERE id = ? AND status = 'pending'`), but
**the return value ignored whether the swap succeeded**: a caller that lost the
race still returned the job dict to its worker.

Measured before changing anything — 8 threads on a `threading.Barrier`, one
pending job, 40 rounds:

```
38/40 rounds handed one job to multiple workers, e.g. (0, [1, 1, 1, None, 1, 1, 1])
draining a 60-job queue from 8 threads: jobs claimed more than once: [1, 3, 5, 52, 58]
plus repeated sqlite3.InterfaceError: bad parameter or other API misuse
```

Six workers received the same job in a single round. The `InterfaceError` is
separate and structural: Python's `sqlite3` is threadsafety level 1, so one
connection shared across threads must be serialised externally or it raises.

This is not theoretical. `scripts/mac_worker.py` polls this queue over HTTP and
`scripts/batch_controller.py` runs parallel encodes — two workers claiming one
job means the same file encoded twice, both writing the same `_opt.` output.

#### The fix

`get_next_pending` now holds the lock across the claim and honours
`cursor.rowcount`: losing the compare-and-swap means looping to the next
pending job, never returning one the caller does not own. The lock was extended
to the rest of the `encoding_queue` surface — `queue_encode` (its check-then-
insert had the same shape of race, allowing duplicate pending jobs for one
file), `update_job_status`, `get_queue_status`, `cancel_job`, `is_job_cancelled`,
`cleanup_old_jobs`.

Changed to `threading.RLock`: `_notify_change` fires *inside* the lock in
`upsert`, so once reads are locked too, any callback re-entering the store would
deadlock on a plain `Lock`. Today the only callback is `_media_cache.invalidate`
(takes its own lock, never touches the store), so this is insurance rather than
a live fix — but the existing `test_write_lock_exists` asserted
`isinstance(..., threading.Lock)` and had to be updated; it now checks
reentrancy behaviourally rather than by type.

**Tests:** 4 added to `tests/test_sqlite_store.py` — barrier-synchronised
single-job contention, concurrent drain of a full queue, claim marks the row
`downloading` and a second caller gets `None`, and duplicate-file queueing is
rejected. Verified failing before the fix (2 failed with the numbers above) and
passing after, re-run 5× for flakiness.

#### Left deliberately unfixed

Reads on the **media** path (`get_all`, `get_page`, `count`, `get`, …) still
touch the shared connection without the lock, so the same `InterfaceError` is
reachable when a dashboard read overlaps a write. Fixing it properly is a design
choice, not a patch: serialise every read through the one connection (simple,
but the dashboard's full-table reads then queue behind writes), or give each
thread its own connection as the class docstring already wrongly claims
("Thread-safe via per-thread connections + write lock"). The second option is
tempting but risky here — `ThreadingTCPServer` spawns a thread per request, so
per-thread connections would open one file handle per request, and this project
has already been bitten once by "Too many open files" (CHANGELOG 6.4.1).
That trade-off wants a waking decision, so it is queued below rather than
guessed at 3am.

**Proposed for the morning:** delete
`origin/fix-json-store-concurrency-8952611763497830264`.
